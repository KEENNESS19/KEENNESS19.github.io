# 整机联调流程

**一句话定义：联调 = 把模块间的隐式假设显式化并逐条验证——bug 不在模块里，在模块之间的接缝里。**

## 内核：为什么单测全绿还会出鬼

单元测试验证的是"给定输入得到给定输出"，但模块之间的协作依赖五类**没有写进接口签名的假设**：

1. **时钟**：双方认为的"同时"差几个毫秒（[[数据回放与时间同步]]的语义问题）；
2. **坐标系**：这个点在基座系还是工具系？z 朝上还是朝前？（[[坐标变换与齐次矩阵]]的记号之争）；
3. **单位**：角度是度还是弧度？力矩是 Nm 还是 kgf·cm（舵机厂商口径不一）；
4. **方向**：正转是顺时针还是逆时针？推指令 +1 它往哪动？
5. **时序**：上电顺序、首帧数据前的行为、心跳丢失后的动作。

单测过不了关的从来不是这五类——它们只在**接缝**处发作。联调的本质：**把五类假设变成一张显式检查单，逐条在真实链路上验证**。

## 规则与行为

**先定流程，再写脚本**（这条是工作方式而非技术）：联调脚本会把检查单里验证过的假设**固化**下来（固定的上电序列、固定的零位、固定的坐标系定义），脚本本身是检查单的可执行形态——检查单变了脚本重写，顺序不能反。

**分阶段集成规则**（每阶段只引入一个新变量）：

1. **单模块自检**：每个模块带着假数据源独立跑（假 IMU、假关节）；
2. **链路集成**：两两相连——传感器→融合、融合→规划、规划→执行，每条链路用已知输入验证输出（推一下机器人，看位姿估计方向对不对）；
3. **整机空载**：全链路跑标准动作序列，录包（[[数据回放与时间同步]]）；
4. **整机带载**：真实负载 + 异常注入（挡一下、拔一个传感器、断一次电）。

**联调检查单**（最小集，每台新机器过一遍）：

- [ ] 全部模块时钟同源，时间戳打在采集层；
- [ ] TF 树画出打印稿，每个坐标系 z 朝哪写清楚；
- [ ] 单位约定表（角度/长度/力矩/电流）贴在仓库 README；
- [ ] 每个关节 +指令方向实测记录（正指令往哪转）；
- [ ] 上电/下电顺序表，急停链路单独演练；
- [ ] 传感器失效各拔一遍，整机进入预期安全态。

## 抽象：检查单即接口契约文档

抽象后，检查单不是"经验备忘"而是**接口契约的文档化**——它定义的正是签名表达不了的那部分接口（单位、方向、时序、语义）。工程化落点：检查单进版本库、机器状态（外参、零位、增益）做成**机型配置文件**随代码走；新机器联调 = 填配置 + 过检查单 + 跑标准脚本。联调从"老师傅的手艺"变成"可重复的流程"——这也是下一篇文章[[测试方法论]]的地基。
