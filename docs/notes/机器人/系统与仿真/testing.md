# 测试方法论

**一句话定义：机器人测试 = 在真实世界不可复现的约束下，用"逐层固化随机性"的办法让问题可重复、指标可比较、回归可执行。**

## 内核：为什么机器人测试比软件测试难

普通软件的输入是确定的，机器人软件的输入是**物理世界**——同一份代码今天跑和明天跑，光照、地面、电池电压、传动温度都不同。于是"上次好的现在坏了"三种可能：代码退化、环境变了、器件漂移（[[编码器]]零位、[[减速器]]温升）。测试方法论的内核动作：**把三者解耦**——

- 环境随机性 → 仿真固化世界（同一场景种子可重跑）；
- 现场随机性 → 录包固化现场（[[数据回放与时间同步]]）；
- 器件随机性 → 标定与自检固化状态（[[传感器标定]]）。

解耦之后，"坏了"总能归位到某一层，修复才有的放矢。

## 规则与行为

**测试金字塔规则**（越往上越贵越慢，问题尽量在下面拦住）：

| 层 | 固化什么 | 速度 | 拦截什么 |
|----|---------|------|---------|
| 单元测试 | 输入输出 | 秒 | 逻辑错误（变换、解析、状态转移） |
| 仿真集成 | 世界 + 全软件链 | 分钟 | 模块接缝、时序、参数 |
| HIL 硬件在环 | 真硬件 + 虚世界 | 分钟–小时 | 实时性、驱动、总线 |
| 整机场景 | 真机 + 真世界 | 小时 | 真实环境的最终确认 |

规则：**代码合并前必须过单测 + 仿真回归；整机场景只做抽样确认**——把整机时间留给仿真拦不住的问题。

**指标体系规则**：每个动作定义可测指标（到位精度/完成时间/成功率/异常恢复率），每次测试输出**与历史可比的数字**而不是"感觉还行"。指标要配测试条件（负载/电池电压/温度）——不带条件的成功率没有意义。舵机类测试的最小指标集：零位重复性、定位精度、响应延迟、温升曲线、堵转保护。

**消融规则**：改了两个变量后性能变化，无法归因——**一次只动一个变量**，其余用上一条的可比指标冻结。这与[[整机联调流程]]"每阶段只引入一个新变量"是同一纪律的两面。

**异常注入规则**：正常路径人人会测，故障路径不注入永远不执行——拔传感器、掉包、电压跌落、堵转，逐项注入并核对进入预期安全态（与联调检查单共享用例）。

## 抽象：测试即资产

抽象后，测试的产出不是"通过/失败"，而是三类**资产**：可重放的录包库（问题复现用例）、可自动执行的回归脚本（[[整机联调流程]]标准脚本的延伸）、带条件的指标历史（性能退化趋势）。三者进 CI 的闭环：**每次提交 → 仿真回归 → 指标对比 → 超阈值报警**。至此"先明确流程、再写脚本"的工作方式有了完整落点：流程固化成检查单与脚本，脚本产生资产，资产反过来守护流程。
