# 软件架构模式

**一句话定义：架构 = 三个决策的集合——共享状态放在哪、数据沿什么方向流、故障在哪个边界被隔离。**

## 内核：复杂度的三个来源

机器人软件为什么比一般软件容易腐化？三个结构性的复杂度来源：

1. **多速率**：控制 1 kHz、感知 30 Hz、规划 10 Hz、UI 1 Hz——同一份状态被不同节奏的模块读写；
2. **多模块**：感知、决策、执行各自迭代，接口却是隐式约定；
3. **共享状态**：机器人的"当前位姿/当前任务/当前模式"天然是全局事实，谁都想直接读改。

三个来源叠加的典型事故：某模块以 10 Hz 写的状态被 1 kHz 的控制环以 1 kHz 读——读到一半被改写，现象是"偶发、不可复现"。**架构的所有模式，都是对这三个来源的正面回答。**

## 规则与行为

**状态归属规则**：每个状态量有唯一写入者（owner），其他人要么订阅消息、要么读带版本号的状态存储。**判断标准：谁产生这个量，谁写它**——位姿由定位模块产生，其他模块只有阅读权。这一条直接消灭"两个模块同时修正位姿"类的打架。

**数据流向规则**：分层单向流——感知 → 融合 → 决策 → 执行，反馈通过执行器作用于世界再进感知，**不在软件里开旁路循环**。跨层的快速通道（如安全停止）单独立项并保持极简（见安全软件规则）。分层的依据不是"逻辑上的高低贵贱"而是速率与失效隔离（[[混合决策架构]]的分层判据同源）。

**通信形态规则**：

| 数据形态 | 用法 | 例 |
|---------|------|-----|
| 持续流 | 话题/队列，可丢旧值 | 传感器读数、位姿 |
| 请求-响应 | 服务调用 | 查询参数、触发标定 |
| 长事务 | 动作（进度 + 可中止） | 导航、抓取任务 |
| 共享事实 | 带版本的状态存储/TF | 当前位姿、模式 |

**故障隔离规则**：故障边界 = 进程/节点边界。会崩的（视觉推理）、要实时的（控制）、要常改的（行为）分进程部署；边界上的契约是消息 schema + QoS + 心跳，**边界内实现随便改**（与 pimpl 思想同构：冻结接口，自由实现）。见[[DDS]]的 QoS 契约与[[ROS 2 体系]]的组件化。

## 抽象：数据驱动 + 注册表

两个反复出现的抽象值得单独立牌：

1. **数据驱动的动作管理**：动作定义成数据（参数化的基元描述 + 触发条件），运行时按数据分发执行——动作库/任务分发系统的核心模式。收益：加动作不改框架，动作可序列化可下发（机制与策略分离）。
2. **注册表/工厂**：能力（节点类型、动作类型、插件）以名字注册，运行时按名实例化——BT 的节点工厂、ROS 2 的插件lib、乃至本站博客的 React 插件系统都是同一抽象。**静态语言里"结构即数据"的标准代价与标准答案。**

架构评审时的三个问题，正好对应三个内核来源：**这个状态谁写？这条数据为什么往这流？这个模块崩了谁活着？**——答不清任何一个，架构就有洞。
