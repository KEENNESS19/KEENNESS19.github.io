# 状态机原理：从需求到状态爆炸

> 同一套方法：不背定义，从需求出发推导。FSM 是最古老的决策模型，它的每个性质（确定性、互斥状态、显式转移）都来自一个朴素需求——**让"系统现在该做什么"有一个唯一、可枚举、可验证的答案**。它的局限（状态爆炸）也同样从需求推导出来。

---

## 1. 为什么需要形式化的状态模型

任何会与事件交互的系统（机器人任务层、通信协议、游戏 AI、UI）都面临同一个问题：**同一个输入，在不同"处境"下应该有不同反应**。电梯收到"开门"，在静止楼层时是开门，在运行中是忽略，在故障时是报警——行为依赖于历史。

处理"依赖于历史"有两条路：

1. **隐式**：散落在代码各处的 `if` 和布尔标志位（`is_running && !is_faulted && has_task`）——历史被编码成任意多的 bool，组合状态数指数增长，而"当前处于什么状态"这个问题没有唯一答案；
2. **显式**：承认系统在任意时刻处于**有限个互斥处境之一**，处境之间的切换规则集中定义——这就是有限状态机。

FSM 的本质是**把"依赖历史的控制流"压缩成"一个变量 + 一张转移表"**。这不是实现技巧，是建模决策：它强迫设计者枚举所有处境、显式定义每条边，于是"漏掉某个输入的处理"在设计图上直接可见（缺边），而在 if-else 代码里不可见（静默错误）。

## 2. 数学定义：五元组每个元素为什么存在

确定型 FSM 定义为 $(S, \Sigma, \delta, s_0, F)$：

- **S**：有限状态集。**互斥**是核心约束——任一时刻只处于一个状态。互斥保证了"当前状态"是单一事实来源，也为运行时断言（不可能同时既走又停）提供了形式基础。
- **Σ**：输入事件字母表。事件驱动的一切输入都必须落在枚举内——**未定义的事件在形式上是非法的**，工程上对应"忽略/告警"，但必须显式写出来。
- **δ: S × Σ → S**：转移函数。完全性（total function）是可选的加强：要求每个 (状态, 事件) 组合都有定义。工程 FSM 常用**部分函数**（缺省为忽略）+ 显式默认处理，平衡严格性与简洁。
- **s₀**：初始状态。消除"系统刚启动处于什么状态"的歧义。
- **F**：接受态集合（形式语言视角）；在控制视角通常退化为终止状态或不存在。

**为什么五元组值得背下来？** 因为它是**可验证性**的来源：S 和 Σ 有限 → 可以画完整的状态图；δ 是函数 → 可以做可达性分析、死锁检测（无出边的非终止态）、等价类合并（两个状态对所有输入行为相同则合并）。布尔标志位方案没有任何一种这样的分析工具。

## 3. Moore vs Mealy：输出挂在哪里

两种经典变体的区别只有一个：**输出由什么决定**。

- **Moore 机**：输出 = f(状态)。进入状态即输出，输出在状态停留期间稳定。
- **Mealy 机**：输出 = f(状态, 输入)。输出是转移的附属品，可以比 Moore 少状态（同一行为）但输出与时钟沿绑定，可能出现毛刺。

**为什么机器人/嵌入式领域偏爱 Moore？** 因为控制输出（电机使能、指示灯、模式信号）需要**稳定持续**的电平，而不是瞬时脉冲；且 Moore 的输出在状态图上可读（状态框里写输出），review 时一目了然。Mealy 的紧凑性在协议解析（输出与输入符号一一对应）场景才占优。实践共识：**控制类用 Moore，解析类用 Mealy，混合使用也常见**。

## 4. 状态爆炸：FSM 的阿喀琉斯之踵

### 4.1 机制：两个正交维度的笛卡尔积

一个移动机器人有任务模式（待机/巡逻/作业）与电源模式（正常/低电/充电）两个正交维度，扁平 FSM 需要 3 × 3 = 9 个状态、边数随维度乘法增长。N 个独立维度各 m 态，扁平 FSM 是 $m^N$ 个状态。更糟的是**转移的重复**：无论处于哪个任务模式，"低电 → 充电"这条边都要从 3 个状态各画一次——一条全局规则被复制 N 份，改一处漏两处。

### 4.2 解法一：层级状态机（HSM）

UML Statechart（Harel, 1987）的答案：**状态可以嵌套**。把"电源模式"做成父状态，任务模式作为子状态画在里面，"低电"转移只画在父状态边界上一次，**子状态隐式继承父状态的所有转移**。机制上，事件分派由内向外冒泡（innermost handler first），父状态处理子状态不处理的事件——与 GUI 事件冒泡同构。

HSM 保留了 FSM 的全部可验证性（仍是有限状态，只是图有了层级），同时把状态数从乘法降为**加法**：两个维度 3+3=6 个节点表达 9 个组合状态。

### 4.3 解法二：正交区域

Statechart 进一步允许**并发正交区域**：两个维度各自独立运行状态机，系统状态是它们的组合。代价是区域间同步需要显式的事件协调，复杂度回升——实践原则：**正交区域是最后手段，优先用层级和守卫条件**。

## 5. 实现模式：从 switch 到状态类

- **switch/枚举**：状态是枚举值，转移函数是一个大 switch。最直白，适合状态少于 10 个的场景；缺点是所有逻辑集中一处，违反开闭原则。
- **表驱动**：转移表 (state, event) → (next_state, action) 用数据结构表达。表可序列化、可由工具生成校验，适合协议机。
- **状态模式（面向对象）**：每个状态一个类，实现统一的 `handle(event)` 接口，Context 持有 `unique_ptr<State>` 持有多态分派（机制同 C++ 原理 1.4 的 vtable）。转移 = 替换指针。优点：状态内逻辑内聚、新状态不改旧代码；缺点：类数量膨胀，全局转移（HSM 继承边）难以表达——所以 HSM 库（如 QP/QM、boost::sml）通常是表驱动 + 层级框架，而不是朴素状态模式。
- **现成框架**：ROS 生态的 SMACH、Boost.SML、QP 框架——选型标准是是否需要层级（HSM）和是否需要运行时可视化。

关键工程细节：**转移动作与进入/退出动作的分离**。进入动作（entry）、退出动作（exit）、转移动作（transition）三者的执行顺序必须有定义（Statechart 标准：先 exit 源、再 transition、后 entry 目标），否则"转移途中的副作用顺序"就是未定义行为——这是自研 FSM 最常见的坑。

## 6. 事件驱动 vs 轮询：FSM 的两种心跳

- **事件驱动**：事件队列驱动转移，无事件时状态机静止。响应快、CPU 友好，但**转移时机不可预测**（事件风暴下的顺序敏感），且与主循环的时序解耦后，调试要追异步踪迹。
- **轮询（tick 驱动）**：主循环每帧喂一次 `update()`，内部检查条件决定是否转移。时序完全可预测（同行为树的 Tick 模型，见行为树篇 6.2），适合与固定频率的感知-控制回路集成。

机器人的任务层 FSM 通常是轮询式（挂在 10–100 Hz 的控制循环上），通信协议 FSM 是事件驱动——按"转移条件来自哪里"选择：来自外部异步事件用事件驱动，来自周期性感知状态用轮询。

## 7. 与行为树的边界：什么时候还用 FSM

行为树篇会详细论证 BT 如何解决 FSM 的组合性问题（行为树篇 6.1），但 FSM 在以下场景仍是正确答案：

- **真状态语义**：系统确实有"互斥的物理模式"（充电/运行/故障），互斥是硬件事实而不是建模选择——FSM 的互斥约束是**忠实表达**而非限制；
- **转移密集且显式**：协议、工作流、硬件握手，每条边都是"必须被 review 的契约"——FSM 的转移表正是契约清单；
- **形式化验证**：需要模型检查（TLA+/SPIN）时，FSM 的五元组是直接输入，BT 的树形结构不是标准验证对象。

实践中的成熟分工：**模式切换层用 FSM/HSM（少量状态、硬约束、可验证），行为执行层用 BT（可组合、可扩展、可打断）**，BT 的叶子节点再委托给 DMP 等运动基元（DMP 篇）。三层各自回答一个问题：是什么模式（FSM）→ 该做什么、如何应变（BT）→ 怎么动（DMP）。

## 8. 结语

FSM 的推导链：**行为依赖历史 → 显式化历史 → 有限互斥状态 + 转移函数 → 可枚举、可画图、可验证**；它的失效链：**正交维度相乘 → 状态爆炸 → 转移重复 → 层级化（继承边）或组合化（换成行为树）**。理解这两条链，FSM 就不是一个要背的模式，而是"互斥处境"这个概念的自然形式化，以及它的边界。
