# 行为树原理：Tick 模型与可组合的决策

> 与状态机篇同一推导方法。C++ 原理篇第 6 部分从实现角度（所有权、虚函数）拆过行为树，本篇是完整版：从"FSM 差在哪"出发，把行为树的每个设计决策还原成对那个缺陷的回应。

---

## 1. 起点：FSM 的组合性困境

[[状态机]]篇 4.1 论证过 FSM 的两个结构性缺陷：

1. **状态爆炸**：行为维度正交时状态数相乘；
2. **边即逻辑**：转移规则分散在每条边上，行为复用单位是"状态对"，无法整体搬移。

根本原因在于 FSM 的组合单位是**状态**，而状态之间靠**边**连接——组合行为时边是手工布线的。机器人任务层需要的是另一种组合单位：**把"一坨行为"当作一个整体，像积木一样嵌进更大的行为**。行为树的所有设计都围绕这个需求展开：用**树形包含**替代**图连线**，让"子行为"天然是父行为的组成部分。

## 2. 节点分类：最小完备的四类积木

行为树的节点可以收敛为四类，每类回答一个问题：

| 类别 | 代表节点 | 回答的问题 | 返回值逻辑 |
|------|---------|-----------|-----------|
| 组合节点 | Sequence、Selector、Parallel | **子行为怎么编排** | Sequence：全成功才成功（逻辑 AND）；Selector：一成功即成功（逻辑 OR）；Parallel：同时 tick 按 policy 汇总 |
| 装饰节点 | Retry、Timeout、Inverter、ForceSuccess | **怎么修饰一个子树** | 包装单个子节点，变换其返回值或生命周期 |
| 执行节点 | Action、Condition | **真正做事** | Action 执行副作用；Condition 只读判定（无副作用） |
| 数据节点 | 黑板读写（常融合在端口里） | **数据从哪来到哪去** | 读写黑板键 |

**为什么恰好这四类？** 因为它们对应控制流的四个正交关注点：**编排（结构）、修饰（横切）、执行（叶子）、通信（数据）**。任何行为树系统无论 API 长什么样，缺了哪类都会在实践里被迫用别扭方式补——例如缺装饰节点时，重试逻辑只能写死在每个 Action 里，无法复用。

**为什么叶子节点要区分 Action 和 Condition？** 因为两者的失败语义不同：Condition 返回 Failure 是**正常信息**（条件不成立，Selector 换下一个分支），Action 返回 Failure 是**异常事件**（任务没做成，需要重试/恢复）。区分它们让"逻辑 OR 换分支"和"失败恢复"两种语义不会混在一起。

## 3. Tick 三态模型：为什么是 Running

执行模型：**每帧从根 tick 一次**，节点返回 `Success / Failure / Running` 三态之一（见 C++ 原理 6.2 的帧驱动论证：确定性与可中断性）。这里补 Running 的推导：

- 长时任务（移动 3 秒、抓取 1 秒）如果同步阻塞 tick，整棵树就死了——其他分支（安全监控）无法运行；
- 如果异步化（任务完成发事件），树失去"每帧重新评估"的能力，退化回事件驱动 FSM 的时序问题；
- **Running 是第三条路**：任务声明"未完成，下帧继续问我"，控制权每帧都交还树根。

三态的关键推论：**树是"每帧从头执行的查询"，不是"一次执行的流程"**。这个心智模型解释了行为树的大多数怪癖——为什么反应式节点要重评估、为什么副作用要小心、为什么异步节点必须实现 halt。

## 4. 反应式 vs 记忆式：重评估的两难

组合节点带 Running 子节点时的核心抉择（C++ 原理 6.4 论证过，此处给出完整的取舍表）：

| 方案 | 机制 | 优点 | 缺点 |
|------|------|------|------|
| 记忆式（Sequence） | 游标记位，下帧从断点继续 | CPU 省；副作用（如"抓取"的进入动作）不重复 | 前序条件陈旧——"敌人不在"早变假了没人再查 |
| 反应式（ReactiveSequence） | 每帧从第一个重评估 | 响应性最好；条件翻转立即打断 | 每帧全量重算；前序节点副作用每帧重放 |

**为什么库同时提供两种而不是选一种？** 因为两者的失效模式恰好互补，正确选择取决于子树的语义：**纯条件的子树用反应式（重评估是目的），有副作用的子树用记忆式（重放是 bug）**。这是一个"机制二选一、语义由用户判断"的典型设计。BT.CPP 的经验法则是：默认 ReactiveSequence，出现"动作被执行两次"才换记忆式。

推论（C++ 原理 6.6）：**Running 的组合节点必须带记忆（执行游标），但记忆的范围仅限控制流；数据一律走黑板**。控制流有状态、数据流无状态，是行为树正确性的第一纪律。

## 5. 黑板：树外数据总线

节点之间为什么不能直接互相调用、共享成员？因为**树形包含结构里，兄弟节点唯一的公共祖先是根**——任何直接引用都会在子树搬移时断掉（组合性的反面）。黑板（C++ 原理 6.3）用"节点只认键不认对象"解决：兄弟节点通过黑板键交换数据，子树整体搬移后键依赖依然成立。

黑板相对全局变量的三个强化：作用域绑定树实例（每机器人一份，天然隔离）、键带类型、读写依赖可通过端口声明显式化（工具链能画出数据流图）。**黑板是行为树版的依赖注入容器**：解耦来自"依赖通过外部名字解析"而不是"对象直接持有"。

## 6. 恢复与回退：Selector 的工程化

朴素 Selector（从左到右尝试，成功即停）在实践中要加两个机制才可用：

- **优先级即恢复序**：把"恢复行为"（脱困、重试）放左边，"正常行为"放右边——异常时 Selector 自然先试便宜的恢复手段，逐级升级到昂贵的方案。这是行为树里"故障恢复"的标准表达，**不需要写任何恢复状态机**；
- **带条件的回退**：`RetryUntilSuccessful(n)` 装饰器 + 指数退避参数，把"重试几次、间隔多久"从业务代码里抽出来成为可配置横切面。

这套机制对应机器人任务的"teleop → 重定位 → 重试抓取 → 报警"升级链，在 BT 里是三行 XML，在 FSM 里是一张需要维护的转移子图——这就是组合性差异的直观体现。

## 7. 工程实现要点（C++）

C++ 原理 6.5 论证过所有权设计（`unique_ptr` + 虚函数 + 递归析构），本篇补运行时清单：

- **接口**：`Status tick(Blackboard&)` + `virtual void halt()`。halt 是**可中断契约**（C++ 原理 6.8）：任何 Running 节点都可能在下一帧被反应式打断，必须能安全中止（取消导航目标、释放夹爪力控）——漏实现 halt 的异步节点是行为树 bug 的头号来源；
- **树构建**：XML/工厂注册（结构即数据，可与 Groot 等工具共享，策划改树不重编 C++）或 C++ 内联构建（编译期检查，重构友好）。生产环境通常两者并存：开发用内联，部署用 XML；
- **调试**：tick 级日志（每帧每节点的返回值 + 耗时）、黑板快照、树状态可视化——行为是时序过程，可视化是唯一把时序投影回静态结构的手段（C++ 原理 6.7）；
- **性能**：树的遍历是 O(节点数) 的虚调用，百节点规模在控制频率下可忽略；热路径优化方向是减少 Condition 的重复计算（条件结果缓存一帧）而不是优化遍历本身。

## 8. 与 FSM 的混合：BT 包裹 HSM

行为树不擅长表达"真互斥的物理模式"（状态机篇 7），成熟架构是**混合**：

- 顶层 FSM/HSM：充电 / 运行 / 故障等硬模式，互斥是硬件事实；
- 每个模式内部一棵行为树：该模式下的任务编排与恢复；
- BT 叶子再委托运动基元（见[[DMP]]）：生成具体轨迹。

分层依据是**变更频率与正确性来源**：模式层状态少、边是安全契约、几乎不变（FSM 的强项）；行为层频繁调整、需要组合与打断（BT 的强项）；运动层需要数学保证（DMP 的强项）。**每层用它失效代价最低的模型**。

## 9. 结语

行为树的推导链：**FSM 组合性困境 → 组合单位从"状态对"改为"子树" → 树形包含 → 编排/修饰/执行/数据四类节点 → 帧驱动 Tick 保住可中断性 → Running 引出记忆式/反应式两难 → 用语义区分（条件反应式、动作记忆式）收尾**。它的每一个"奇怪"设计（每帧重评估、halt 契约、黑板键）都是"树是每帧重新执行的查询"这一心智模型的必然推论。理解了这个模型，行为树不是需要背的 23 种节点，而是四类积木加上三条纪律：**控制流有记忆、数据流走黑板、副作用可中断**。
