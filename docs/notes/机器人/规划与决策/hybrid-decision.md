# 混合决策架构

**一句话定义：混合决策架构 = FSM 管模式、行为树管行为、运动基元管动作的三层分工，每层只回答自己失效代价最低的问题。**

## 内核：为什么单一模型必然失效

三种决策模型各有一个结构性缺陷（前几篇已推导）：[[状态机]]的组合单位是状态对，行为一多状态爆炸；[[行为树]]的互斥性弱，"物理上只能处于一种模式"的硬件事实要靠纪律保证；[[DMP]]类基元只会执行，没有"该不该执行"的判断。**缺陷的分布恰好互补**——这是混合架构成立的全部理由：

- **模式层（FSM/HSM）**：回答"是什么模式"。状态少（充电/运行/故障）、边是安全契约、几乎不变——FSM 的强项区。
- **行为层（BT）**：回答"做什么、怎么应变"。频繁调整、需要组合与可打断——BT 的强项区。
- **执行层（基元）**：回答"怎么动"。需要动力学保证与抗扰——基元的强项区。

**判据一句话：变更频率与失效代价决定归属。** 把容易变的逻辑放上层，把需要形式化验证的契约放下层。

## 规则与行为

**层间接口只有三个动词**：`start(参数)`、`abort()`、`status()`。为什么是三个：上层对下层的合法操作只有"启动、中止、询问"，**一旦出现"直接设置下层内部状态"的调用，分层立即腐化**（上层开始假设下层的实现细节）。

**职责边界规则**：

1. 模式切换的条件**只**放在 FSM 的转移上，BT 内部不得改模式（否则模式约束失效）；
2. 安全停止的优先级**永远高于**行为逻辑：急停链路绕过 BT 直接作用执行层（见安全软件，软件篇）；
3. 行为层每帧重评估（BT 的 Tick 模型），执行层的 Running 状态通过 `status()` 上浮，成为 BT 分支打断的依据；
4. 数据共享走黑板/状态存储，不走层间直接引用（[[行为树]]黑板规则的延伸）。

**失效排查规则**：行为异常时按层定位——"该切模式没切"查 FSM 转移条件；"切了模式做错事"查 BT 结构与条件节点；"做的事物理上做不赢"查基元参数与执行层反馈。

## 抽象：行为库与模式库——决策层的资产化

三层分工稳定后，每一层的产出都可以**资产化**：模式库（FSM 定义）、行为库（BT 子树，可序列化为 XML）、基元库（DMP 参数集）。任务需求 = 从三个库里取件组装——这正是**动作库 + 任务分发**系统的架构骨架：动作库即基元库（参数化的可执行动作），任务分发即模式层+行为层的运行时。变更频繁的商业逻辑全部落在 BT 的 XML 与基元参数里，C++ 层保持稳定（机制与策略分离，同[[软件架构模式]]的主题）。
